# Миграции базы данных (Prisma 7.10)

## Что изменилось

До версии 0.3 схема жила в `server/schema.sql`: сервер при `npm run db:setup` выполнял его целиком (`CREATE TABLE IF NOT EXISTS` + перенос старых показаний). Запросы писались вручную через `pg`.

Теперь:

| Было | Стало |
| --- | --- |
| `server/schema.sql` | `prisma/schema.prisma` — модели; `prisma/migrations/*/migration.sql` — история изменений |
| `pool.query('INSERT … ON CONFLICT …')` | `prisma.record.upsert(...)`, `createMany({ skipDuplicates: true })` |
| `BEGIN / COMMIT / ROLLBACK` вручную | `prisma.$transaction(async (tx) => …)` |
| jsonb `?|`, `FOR UPDATE`, `SKIP LOCKED` | те же SQL-фрагменты через типобезопасный `` $queryRaw`…${param}…` `` (параметры, без склейки строк) |
| `npm run db:setup` = выполнить SQL | `npm run db:migrate` = `prisma migrate deploy` (применяет только новые миграции) |
| Тесты: PGlite + `schema.sql` | Тесты: PGlite + те же файлы миграций + `pglite-prisma-adapter` |

## Миграции

| Папка | Что делает |
| --- | --- |
| `0_init` | Все таблицы и индексы. В конце вручную добавлено то, что Prisma описать не может: CHECK на `users.role` и `records.kind`, GIN-индекс по `records.data`, уникальный индекс «одно показание на счётчик в месяц» по выражениям из jsonb |
| `1_legacy_meters` | Перенос показаний v0.1 без счётчика на автоматически созданный «Счётчик из истории». Идемпотентна; на новой базе ничего не делает |

Имена таблиц, колонок, первичных и внешних ключей совпадают с прежним `schema.sql`, поэтому существующую базу можно не пересоздавать.

## Сценарии

### Новая база

```bash
npm run db:migrate        # prisma migrate deploy
```

### База, созданная старой версией (до Prisma)

Таблицы уже есть, поэтому `0_init` применять нельзя — его нужно один раз **отметить как применённый**:

```bash
npm run db:baseline       # prisma migrate resolve --applied 0_init
npm run db:migrate        # применит 1_legacy_meters и всё новее
```

Перед этим сделайте `pg_dump`. Признак, что нужен baseline: ошибка `P3005 The database schema is not empty`.

### Изменить схему (разработчику)

1. Поправить `prisma/schema.prisma`.
2. `npm run db:migrate:dev -- --name короткое_имя` на локальной базе — Prisma создаст папку миграции и применит её.
3. Если нужно то, чего нет в Prisma (CHECK, частичный или функциональный индекс), дописать SQL в созданный `migration.sql` до коммита.
4. `npm test` — тесты применяют все миграции к PGlite, так что сломанная миграция сразу видна.
5. Закоммитить `schema.prisma` и папку миграции вместе. Применённые миграции не редактируются — только новые.

### Посмотреть данные

```bash
npm run db:studio         # Prisma Studio в браузере
```

## Почему так

- **Prisma 7.10, а не 8**: на момент перехода 8.x был только release candidate.
- **Драйвер-адаптер `@prisma/adapter-pg`**: в Prisma 7 клиент работает через адаптер, без бинарного движка — меньше образ и холодный старт на Render.
- **snake_case в моделях**: поля называются как колонки, поэтому SQL-фрагменты и код читаются одинаково, а миграция данных не нужна.
- **Сырые запросы оставлены осознанно**: jsonb-операторы и блокировки строк — часть логики прав и очереди; переписывать их на выборку «всё, потом фильтр в JS» значит потерять фильтрацию на уровне БД.

## Откат

Prisma Migrate не делает «down»-миграций. Откат = восстановление из `pg_dump` и деплой предыдущего коммита. Поэтому перед каждым деплоем со схемными изменениями — резервная копия.
